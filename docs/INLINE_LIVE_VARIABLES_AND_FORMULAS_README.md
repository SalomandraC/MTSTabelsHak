# Алгоритм inline-окна для живых переменных и живых формул

## Цель

Inline-окно должно показывать не сырой markdown, а семантически разобранный контент:

- живые переменные отображаются как отдельные inline-сущности;
- живые формулы отображаются как вычисляемые inline-сущности;
- жирный текст, заголовки, списки и другие markdown-элементы выглядят как в итоговом документе, а не как исходная разметка;
- при вставке в основной документ не ломается существующая логика редактора, таблиц, ссылок, автосохранения и коллаборации.

## Главная идея

Нельзя делать простую подстановку строк.

Нужен двухслойный pipeline:

1. Сначала markdown превращается в структурное дерево блоков и inline-узлов.
2. Затем в текстовых участках дерева ищутся live-токены и заменяются на специальные ноды.

Так мы сохраняем форматирование markdown и одновременно поддерживаем живые переменные и формулы.

## Алгоритм

### 1) Классификация входа

Перед обработкой входной текст проходит быструю классификацию:

- есть ли markdown-признаки: заголовки, списки, таблицы, цитаты, жирный текст, code fence, inline code;
- есть ли live-токены: переменные и формулы;
- является ли текст обычным plain text.

Если markdown и live-токенов нет, вставляем текст как есть.

### 2) Markdown-парсинг в семантическое дерево

Если markdown найден, текст нужно парсить в дерево блоков, а не в HTML-строку.

Результат должен содержать:

- heading для заголовков;
- paragraph для обычного текста;
- list / listItem для списков;
- table / tableRow / tableCell для таблиц;
- marks для bold, italic, code и т.д.

Это важно, потому что итоговая вставка в редактор должна сохранить структуру, а не исходные символы markdown.

### 3) Постобработка inline-токенов

После markdown-парсинга проходится рекурсивный обход дерева.

Правило простое:

- если узел текстовый, он сканируется на live-токены;
- если узел блочный, рекурсивно обрабатываются его дети;
- если узел уже является специальным embed-элементом, он не переписывается повторно.

Поддерживаемые live-токены:

- переменная вида `[Ref:datasheetId:recordId:fieldId]`;
- формула вида `[Formula: expression ]` с вложенными скобками внутри выражения.

Каждый найденный токен превращается в отдельную inline-ноду, а окружающий текст остаётся обычным text-node.

### 4) Обработка формулы

Формула разбирается отдельным сканером с учётом вложенных квадратных скобок.

Это нужно, чтобы корректно поддерживать выражения вроде:

- `[Formula: ([Ref:a:b:c] + [Ref:d:e:f]) / 2]`

Алгоритм не должен обрезать формулу на первой закрывающей скобке, если внутри есть вложенные токены.

### 5) Вставка в основной документ

Когда пользователь нажимает Insert в inline-окне, в редактор нужно вставлять не исходный markdown-стринг, а структурированное дерево.

Правило вставки:

- markdown-структуры вставляются как block nodes;
- inline-токены вставляются как inline nodes;
- текст внутри markdown сохраняет mark-структуру, но не сохраняет символы разметки.

Поэтому:

- `**жирный**` превращается в bold text без звёздочек;
- `# Заголовок` превращается в heading node;
- списки, таблицы и цитаты становятся нодами редактора;
- live-формулы и live-переменные остаются живыми объектами, а не строкой.

## Почему это не ломает другую логику

Чтобы не разрушить существующее поведение, алгоритм обязан соблюдать несколько инвариантов:

1. Не делать глобальный regex replace по всему документу.
2. Не преобразовывать уже разобранные узлы второй раз.
3. Не трогать code block, inline code и служебные узлы без явного правила.
4. Не изменять формат сохранения данных, только способ их декодирования для редактора.
5. Использовать один и тот же парсер для preview и для вставки, чтобы UI и документ не расходились.

## Безопасные fallback-сценарии

Если markdown-парсер не смог построить дерево, алгоритм должен деградировать поэтапно:

1. попробовать разобрать как markdown-report;
2. если и это не удалось, вставить plain text;
3. если есть только live-токены без markdown, вставить только inline-ноды.

Это защищает от пустой вставки и от поломки редактора на неожиданном вводе.

## Рекомендуемая схема данных

Для вставки удобно мыслить тремя представлениями одного и того же контента:

- raw source: исходный текст из inline-окна;
- semantic tree: markdown-дерево с live-нормализацией;
- editor JSON: итоговые ноды, готовые для insertContentAt.

Такой подход позволяет:

- показывать корректный preview;
- вставлять корректный документ;
- не терять marks и block-структуру;
- не смешивать визуальный рендер и логику сохранения.

## Псевдокод

```text
function insertFromInlineWindow(text):
    if no markdown and no live tokens:
        insert plain text
        return

    tree = parseMarkdown(text)

    if tree is empty:
        if has live tokens:
            insert inline live nodes
        else:
            insert plain text
        return

    tree = walk tree and replace text spans with live nodes

    insert tree into editor as structured content
```

## Что важно для UX

- inline-окно показывает результат до вставки;
- пользователь видит заголовок как заголовок, а не как `#`;
- жирный текст не сохраняет символы `**`;
- live-формула остаётся редактируемой и вычисляемой;
- один и тот же контент не должен выглядеть по-разному в preview и после вставки.

## Критерии корректности

Алгоритм считается правильным, если выполняются все пункты:

- markdown-текст превращается в структурированный документ;
- жирный текст вставляется без видимых звёздочек;
- заголовки сохраняют уровень и отображаются как headings;
- live-переменные и live-формулы остаются отдельными сущностями;
- повторная вставка не дублирует обработку токенов;
- соседняя логика редактора продолжает работать без изменений.

## Итог

Лучший вариант для этой задачи — не отдельный “умный replace”, а общий семантический pipeline:

raw text -> markdown AST -> live-token mapping -> editor JSON -> insert

Именно он даёт корректный результат для inline-окна, сохраняет форматирование markdown и минимизирует риск сломать остальной редактор.
