# Анализ API MWS Tables для кейса WikiLive

## Зачем нам этот API

Наша задача не в том, чтобы повторно построить Tables внутри вики, а в том, чтобы встроить существующие сущности MWS Tables в текстовый редактор как живые блоки.

Из предоставленного API видно, что MWS Tables уже дает нам зрелую модель табличных сущностей:

- пространства (`spaces`)
- ноды пространства (`nodes`)
- таблицы (`datasheets`)
- поля (`fields`)
- записи (`records`)
- представления (`views`)
- вложения (`attachments`)
- частичную историчность через `timemachine`

Это означает, что редактор WikiLive должен хранить не сами таблицы, а ссылки на них и метаданные встраивания. Таблица внутри текста должна быть `live reference` на объект MWS Tables, а не копией данных.

## Главный вывод

Для нашей задачи API MWS Tables закрывает контур `поиск/выбор/чтение/частичное изменение` табличных сущностей, но не закрывает контур `wiki pages + backlinks + CRDT collaboration + rich text`.

Следовательно:

- MWS Tables остается системой-источником для таблиц
- наш backend становится системой-источником для страниц, связей между страницами и CRDT-состояния редактора
- в текстовом редакторе таблица хранится как embed-узел с идентификаторами MWS Tables сущностей

## Что в API особенно полезно для нас

### 1. Пространства

`GET /fusion/v1/spaces`

Что дает:

- список пространств, доступных пользователю
- стартовую точку для выбора контекста, в котором ищется таблица

Как использовать:

- в slash-меню команда `/table`
- сначала показываем список spaces пользователя
- затем внутри выбранного space даем поиск таблиц и других нод

Практическая польза:

- позволяет встроить редактор в экосистему MWS Tables без ручного ввода идентификаторов
- можно автоматически ограничивать выбор таблиц только теми пространствами, к которым у пользователя есть доступ

### 2. Ноды пространства

`GET /fusion/v1/spaces/{spaceId}/nodes`
`GET /fusion/v1/nodes/{nodeId}`

Что дает:

- древо элементов внутри пространства
- список нод по типу
- метаданные конкретной ноды

Почему это очень важно:

- именно через nodes мы можем строить picker существующих сущностей в редакторе
- это лучший кандидат для UI "вставить существующую таблицу из Tables"

Как использовать:

- в модальном окне выбора таблицы показывать структуру пространства
- фильтровать `type`, если тип таблицы известен
- получать `id`, `name`, `type`, права, возможно дочерние элементы

Что это дает в UX:

- таблица выбирается как реальный объект экосистемы
- пользователь чувствует, что работает не с внешним линком, а с нативной сущностью продукта

### 3. Таблицы как datasheets

`POST /fusion/v1/spaces/{spaceId}/datasheets`
`DELETE /fusion/v1/spaces/{spaceId}/datasheet/{dstId}`

Что дает:

- создание таблицы
- удаление таблицы

Что это значит для нас:

- минимально для MVP нам не обязательно создавать таблицы из вики
- но для сильного сценария можно дать `/table new` прямо в редакторе: создать datasheet и сразу встроить его в страницу

Продуктовый сценарий:

- PM пишет документ спецификации
- через slash-menu создает таблицу требований/рисков/экспериментов
- таблица сразу появляется внутри страницы

Для хакатона это может быть сильной дополнительной функцией, но не обязательной для первого контура.

### 4. Записи таблицы

`GET /fusion/v1/datasheets/{dstId}/records`
`POST /fusion/v1/datasheets/{dstId}/records`
`PATCH /fusion/v1/datasheets/{dstId}/records`
`DELETE /fusion/v1/datasheets/{dstId}/records`

Это один из ключевых блоков API для нашего решения.

Что дает:

- чтение строк таблицы
- создание строк
- обновление строк
- удаление строк
- выбор конкретного view
- фильтрацию формулой
- пагинацию
- ограничение по полям
- сортировку
- возврат значений в `string` или `json`
- выбор ключей полей по `name` или `id`

Как это использовать в редакторе:

- рендер встроенной таблицы прямо внутри страницы
- показывать компактный live preview таблицы
- открывать "expanded table panel" по клику на embed
- реализовать inline-редактирование строк в пределах embed-блока

Самая важная мысль:

- наш embed не должен хранить снапшот строк
- embed должен хранить `spaceId`, `dstId`, опционально `viewId`, конфигурацию отображения и кеш последней успешной загрузки
- реальные строки нужно подтягивать из MWS Tables API

Практические режимы использования:

- `read-only live embed` для MVP
- `read-write embed` как усиление: редактирование записей прямо из страницы

Что особенно полезно из параметров:

- `viewId`: позволяет встроить не всю таблицу, а конкретное представление
- `fields`: позволяет ограничить колонки для компактного embed
- `pageSize`: позволяет делать легкий preview на 5-20 строк
- `filterByFormula`: позволяет встраивать "живые срезы" таблиц в текст
- `fieldKey=id`: лучше использовать для стабильной интеграции, чтобы не ломаться при переименовании полей
- `cellFormat=json`: полезнее для корректного рендера сложных типов

Самый сильный сценарий для нас:

- в тексте можно вставить не просто таблицу, а "представление таблицы" или "срез таблицы"
- например блок "Открытые баги frontend" или "Риски релиза" как живой вид на данные

### 5. Поля таблицы

`GET /fusion/v1/datasheets/{dstId}/fields`
`POST /fusion/v1/spaces/{spaceId}/datasheets/{dstId}/fields`
`DELETE /fusion/v1/spaces/{spaceId}/datasheets/{dstId}/fields/{fieldId}`
`PATCH /fusion/v1/datasheets/{dstId}/views/{viewId}/fields/{fieldId}`

Что дает:

- чтение схемы таблицы
- создание колонок
- удаление колонок
- изменение порядка полей в представлении

Почему это важно:

- без `fields` мы не сможем качественно рендерить embed
- именно schema-first подход позволяет корректно отрисовать типы колонок

Как использовать:

- при вставке embed сначала загружать fields и views
- в UI настроек embed давать выбрать:
- какие поля показывать
- в каком порядке
- какую view использовать

Что можно сделать сверх минимума:

- через `/table config` прямо из вики создать новое поле в таблице
- например "Добавить колонку Status" без выхода из документа

Полезные типы полей для нас:

- `Attachment`: вложения в таблице можно превьюшить в embed
- `Member`: можно показывать ответственных
- `DateTime`: дедлайны и сроки
- `OneWayLink`, `TwoWayLink`, `MagicLookUp`: дают мощный relational story
- `Formula`: можно показывать вычисляемые показатели внутри документа
- `CreatedTime`, `LastModifiedTime`, `CreatedBy`, `LastModifiedBy`: дают прозрачность и доверие к данным

Очень важный вывод:

Таблицы MWS Tables уже умеют быть связанными данными, а не просто grid UI. Это отлично усиливает идею "живой knowledge-platform".

### 6. Представления таблиц

`GET /fusion/v1/datasheets/{dstId}/views`
`POST /fusion/v1/spaces/{spaceId}/datasheets/{dstId}/views`
`DELETE /fusion/v1/spaces/{spaceId}/datasheets/{dstId}/views/{viewId}`
`PUT /fusion/v1/spaces/{spaceId}/datasheets/{dstId}/views/{viewId}`
`POST /fusion/v1/spaces/{spaceId}/datasheets/{dstId}/views/{viewId}/sort`
`POST /fusion/v1/spaces/{spaceId}/datasheets/{dstId}/views/{viewId}/group`
`POST /fusion/v1/spaces/{spaceId}/datasheets/{dstId}/views/{viewId}/hidden`
`POST /fusion/v1/spaces/{spaceId}/datasheets/{dstId}/views/{viewId}/move`

Это, вероятно, второй по ценности блок после records.

Что дает:

- список представлений таблицы
- создание и изменение представлений
- сортировку
- группировку
- скрытие полей
- изменение порядка views

Почему это суперполезно:

- это позволяет нам встраивать в документ не "сырую таблицу", а подготовленный смысловой вид данных

Примеры:

- в PRD показывать только view "Active roadmap"
- в документе по инциденту показывать view "Open incidents"
- в дизайн-документе показывать view "Architecture"
- в планировании показывать `Calendar` или `Gantt`, если это уместно в UI

Что можно сделать в продукте:

- embed-хранилище ссылается не просто на `dstId`, а на пару `dstId + viewId`
- пользователь вставляет таблицу и выбирает нужное view
- при открытии страницы мы берем именно это view и рендерим его как live object

Сильная продуктовая идея:

- embed-блок может иметь режимы отображения:
- `Table`
- `Board`
- `Gallery`
- `Calendar`
- `Architecture`

Если у таблицы уже есть подходящие views, мы используем их как встроенные режимы страницы. Это делает страницу не только текстовой, но и операционной.

### 7. Вложения

`POST /fusion/v1/datasheets/{dstId}/attachments`
`GET /fusion/v1/datasheets/{dstId}/attachments`

Что дает:

- загрузку файлов в таблицу или в конкретную ячейку
- скачивание по token

Как это может пригодиться:

- превью вложений внутри встроенной таблицы
- загрузка файлов в контексте записи прямо из вики-страницы
- генерация карточек с файлами для asset-heavy сценариев

Это не ядро MVP, но хороший усилитель для UX и демонстрации интеграции.

### 8. TimeMachine

`GET /fusion/v1/timemachine/{dstId}`

Что дает:

- массив id удаленных записей

Это не полноценное versioning API, но полезно как технический сигнал.

Как использовать:

- инвалидировать локальный кеш embed-таблицы
- детектить, что ранее видимые записи были удалены
- корректнее обновлять представление без полного несоответствия UI

Ограничение:

- этого недостаточно, чтобы строить полную историю изменений таблицы
- для полноценного audit trail по wiki-страницам все равно нужен наш собственный контур версий

## Что особенно пригодится именно для задачи "встроить сущности в текстовый редактор"

### Сценарий 1. Вставка существующей таблицы в страницу

Это обязательная фича кейса.

Лучший поток:

1. Пользователь вводит `/table`
2. Открывается picker
3. Backend получает spaces
4. По выбранному space backend получает nodes
5. Пользователь выбирает node таблицы
6. Backend получает node details, views и fields
7. Пользователь выбирает:
- таблицу
- view
- какие поля показывать
- режим отображения
8. В документ вставляется embed-узел Tiptap

Что хранить в embed-узле:

- `spaceId`
- `dstId`
- `nodeId`
- `viewId` опционально
- `selectedFieldIds`
- `displayMode`
- `title`
- `lastResolvedAt`
- `cachedPreview` опционально

Критически важно:

- в embed нельзя хранить полное содержимое таблицы как источник истины
- источник истины всегда MWS Tables

### Сценарий 2. Живой preview внутри страницы

Для каждого table embed:

- `GET views`
- `GET fields`
- `GET records?viewId=...&pageSize=...&fieldKey=id&cellFormat=json`

Что можно показывать:

- первые N строк
- число записей
- колонки выбранного view
- индикатор свежести данных
- кнопку "Открыть в Tables"
- кнопку "Развернуть"

Это уже создает ощущение живой таблицы внутри текста.

### Сценарий 3. Inline-обновление данных таблицы из документа

Если мы идем дальше simple-preview, то можно:

- `POST /records` для новых строк
- `PATCH /records` для массового обновления
- `DELETE /records` для удаления

Где это особенно полезно:

- action items на странице встречи
- backlog задач внутри PRD
- список рисков в архитектурном документе

Важно разделять два типа коллаборации:

- коллаборация над wiki-страницей идет через наш CRDT-контур
- коллаборация над данными таблицы идет через API MWS Tables

Это две разные модели состояния, и их нельзя смешивать в одну транзакцию без прослойки orchestration.

### Сценарий 4. Вставка "живой выборки", а не просто всей таблицы

Благодаря `viewId`, `fields`, `sort`, `filterByFormula` мы можем вставлять в текст не любую таблицу целиком, а тематические срезы.

Это очень сильная идея для жюри:

- страница становится не контейнером ссылок, а рабочим узлом знаний
- в одном документе можно собрать несколько data-driven блоков из разных таблиц

Примеры блоков:

- "Открытые задачи релиза"
- "Текущие blockers команды"
- "Кандидаты на A/B тест"
- "Компоненты, затронутые изменением"

### Сценарий 5. Использование relational fields как знания, а не просто данных

Типы `OneWayLink`, `TwoWayLink`, `MagicLookUp` дают нам возможность строить гораздо более сильный knowledge story.

Например:

- одна таблица хранит фичи
- другая хранит риски
- третья хранит UI-компоненты
- через link-поля они связаны между собой

Что это дает в вики:

- внутри embed можно показывать связанные сущности
- можно строить блок "related table entities"
- можно подсвечивать, что текущая страница ссылается на таблицу, где записи сами ссылаются на другие таблицы

Это не равно backlinks между wiki-страницами, но отлично усиливает общую идею graph of knowledge.

## Что API не дает, и что нам придется делать самим

### 1. Нет API для wiki-страниц

Из данной спецификации видно, что API ориентирован на табличные сущности и элементы пространства, но не на rich-text pages.

Значит:

- модель страниц полностью наша
- контент страниц, backlinks и CRDT-хранилище нельзя отдавать MWS Tables

### 2. Нет признаков real-time subscription API

В предоставленной спецификации нет:

- websocket endpoints
- webhook callbacks
- server-sent events
- changefeed по таблицам

Следовательно, по этой спецификации интеграция с таблицами выглядит как request-response.

Практический вывод:

- real-time совместное редактирование страницы должно жить в нашем контуре
- live-обновление embed-таблицы придется делать через polling, explicit refresh или через собственную синхронизацию поверх backend cache

Это важное архитектурное ограничение.

### 3. Нет полноценных версий/ревизий по таблицам

Есть `timemachine`, но только на удаленные record ids.

Значит:

- полноценную историю страницы и откат нужно делать в своей БД
- полноценную audit-модель изменений таблиц на основе этого API не построить

### 4. Не видно поиска по сущностям

Есть spaces, nodes, node details, но из этой выжимки не видно dedicated search API.

Следовательно:

- для picker UI, вероятно, придется:
- либо грузить nodes и искать локально
- либо кэшировать индекс нод на своем backend

Для больших пространств это станет важным.

### 5. Не видно batch API по нескольким datasheet одновременно

Это значит:

- если в странице 5 embed-блоков на разные таблицы, backend должен аккуратно управлять fan-out запросов
- понадобится кэш и дедупликация запросов

## Рекомендуемая модель интеграции в редактор

### Модель данных embed-блока

Для Tiptap я бы хранил отдельный node type, например `mwsTableEmbed`, с такими атрибутами:

- `spaceId`
- `nodeId`
- `datasheetId`
- `viewId`
- `title`
- `icon`
- `displayMode`
- `selectedFieldIds`
- `pageSize`
- `filterByFormula`
- `allowInlineEdit`
- `lastSyncedAt`

Что важно:

- сам CRDT-документ хранит только конфигурацию embed
- данные таблицы живут вне CRDT и подгружаются отдельно

Это очень правильное разделение:

- CRDT синхронизирует структуру документа
- MWS Tables API отдает актуальные бизнес-данные таблицы

### Backend-for-Frontend слой обязателен

Я не рекомендую ходить в MWS Tables API напрямую из браузера.

Почему:

- токены нельзя светить на клиенте
- нужен кэш
- нужна унификация ошибок
- нужна дедупликация запросов
- нужны ограничения по rate/latency
- удобно хранить маппинг embed-конфигураций и server-side enrichment

Правильнее сделать наш backend как BFF:

- frontend -> наш backend
- наш backend -> MWS Tables API

### Рекомендуемый набор backend endpoints

Минимальный интеграционный слой с нашей стороны:

- `GET /api/mws/spaces`
- `GET /api/mws/spaces/{spaceId}/nodes`
- `GET /api/mws/nodes/{nodeId}`
- `GET /api/mws/datasheets/{dstId}/views`
- `GET /api/mws/datasheets/{dstId}/fields`
- `GET /api/mws/datasheets/{dstId}/records`
- `POST /api/mws/datasheets/{dstId}/records`
- `PATCH /api/mws/datasheets/{dstId}/records`
- `DELETE /api/mws/datasheets/{dstId}/records`

Плюс наш собственный агрегированный endpoint:

- `POST /api/wiki/table-embeds/resolve`

Он может за один запрос возвращать:

- node info
- fields
- views
- preview records
- права на inline edit

Это сильно упрощает клиент.

## Какие сущности MWS Tables реально стоит интегрировать в первую очередь

### Обязательный приоритет

1. `Spaces`
2. `Nodes`
3. `Datasheet records`
4. `Fields`
5. `Views`

Этого уже достаточно, чтобы сделать:

- picker таблиц
- вставку таблицы в страницу
- живой preview
- выбор представления
- ограничение колонок
- обновление записей из embed

### Второй приоритет

1. `Attachments`
2. `Create datasheet`
3. `Create field`
4. `Create view`

Это уже даст "операционные" сценарии прямо из документа.

### Третий приоритет

1. `Timemachine`
2. операции скрытия/группировки/сортировки/переупорядочивания view

Это полезно, но для MVP необязательно.

## Какие продуктовые фичи можно красиво показать жюри на основе этого API

### 1. Slash-команда вставки таблицы

`/table`

В результате:

- открывается picker по пространствам и нодам
- выбирается существующий datasheet
- выбирается view
- встраивается live block

Это напрямую закрывает обязательную фичу.

### 2. Встраивание не только таблицы, но и представления

`/view`

Встраивается:

- grid
- kanban
- gallery
- calendar
- architecture

Если в UI сделать это аккуратно, это будет очень сильный differentiator.

### 3. "Данные внутри документа"

На странице можно держать:

- текстовый контекст
- live таблицу задач
- live таблицу рисков
- связанные сущности

То есть страница становится управляющим центром, а не статичной заметкой.

### 4. Создание таблицы по ходу написания документа

`/new table`

Сценарий:

- автор пишет документ
- понимает, что нужен structured data block
- создает datasheet, не уходя из контекста
- сразу заполняет и использует его в тексте

### 5. AI-сценарий поверх таблиц

Даже без отдельного API поиска можно сделать AI-функции поверх уже загруженных schema/records:

- "суммаризируй эту таблицу"
- "выдели риски по записям"
- "создай action items из выбранных строк"

Но это не должно быть в ядре первой версии.

## Ограничения и риски интеграции

### 1. Права доступа

Права есть в нодах и авторизации, но тонкая permission-модель в этой выжимке не раскрыта.

Следовательно:

- backend должен быть готов к `401/403`
- UI должен уметь показывать `нет доступа`, `таблица удалена`, `view больше не существует`

### 2. Хрупкость по именам полей

API позволяет `fieldKey=name`, но это рискованно.

Рекомендация:

- в интеграции везде использовать `fieldKey=id`
- имена полей использовать только для отображения

### 3. Нагрузка на API при множестве embed-блоков

Если на странице много таблиц:

- нельзя по каждому рендеру ходить напрямую в upstream
- нужен server-side cache и stale-while-revalidate

### 4. Изменчивость схемы таблиц

Колонки могут:

- переименовываться
- скрываться
- удаляться
- менять порядок

Следовательно:

- embed должен быть устойчив к отсутствующим полям
- конфигурация embed не должна падать, если поле исчезло

### 5. Две параллельные модели синхронизации

У нас есть:

- CRDT синхронизация страницы
- API-синхронизация данных таблицы

Их нужно явно развести в архитектуре и UX.

Например:

- изменение текста страницы синхронизируется мгновенно между участниками
- обновление таблицы может показывать отдельный loading/apply state

## Самая правильная архитектурная позиция для защиты

На защите я бы формулировал так:

`WikiLive не дублирует MWS Tables, а превращает существующие таблицы, представления и связи данных в встроенные live-блоки знания внутри совместно редактируемых страниц.`

Это звучит сильно, потому что:

- мы не спорим с продуктом Tables
- мы усиливаем его новым уровнем knowledge UX
- мы используем существующие сущности платформы как native building blocks редактора

## Итоговый ответ на главный вопрос

Да, существующие сущности MWS Tables очень хорошо интегрируются в текстовый редактор через это API.

Лучше всего использовать:

- `spaces` и `nodes` для поиска и выбора существующих сущностей
- `views` для выбора правильного смыслового представления таблицы
- `fields` для построения schema-aware embed
- `records` для live preview и inline editing
- `attachments` для richer content blocks
- `timemachine` как вспомогательный сигнал для актуализации кеша

При этом:

- страницы, backlinks, CRDT и versioning должны оставаться в нашей системе
- таблицы и их данные должны оставаться источником истины в MWS Tables
- embed внутри Tiptap должен хранить только ссылку и конфигурацию отображения

Именно такая модель даст нам нативную интеграцию, честную архитектуру и сильный продуктовый сценарий для хакатона.
