# Внедрение ролевой модели доступа для редактора документов

## Описание задачи

Необходимо внедрить в WikiLive page-level систему доступа к документам, которая управляет:

- просмотром документа
- редактированием документа
- комментированием документа
- отображением доступности документов в workspace
- поведением collaborative editing для пользователей с ограниченными правами

Система должна работать не через персональные шаринги, а через настройки доступа самого документа. На первом этапе права задаются не для конкретных пользователей, а для категорий доступа:

- только владелец
- участники пространства
- все, у кого есть ссылка

Итоговая роль пользователя в документе вычисляется не вручную, а из настроек документа и контекста пользователя.

## Цель MVP

Сделать единый и понятный механизм, который позволит:

1. Владельцу документа управлять доступом к документу.
2. Автоматически определять, кем является пользователь для конкретного документа: owner, editor, commentator, guest.
3. Ограничивать действия в backend и frontend в зависимости от вычисленной роли.
4. Поддержать анонимный доступ по ссылке без отдельного логина.
5. Не ломать текущий demo-flow редактора, комментариев, коллаборации и workspace tree.

## Ролевая модель

### Базовые роли

- `owner`:
  владелец документа, имеет полный доступ к документу и настройкам доступа
- `editor`:
  может просматривать, редактировать, комментировать документ, но не может удалять документ и не может менять настройки доступа
- `commentator`:
  может просматривать документ и работать только с комментариями
- `guest`:
  может только просматривать документ

### Важные ограничения

- владелец у документа только один
- персональные назначения прав конкретным пользователям в MVP не поддерживаются
- наследование прав от папки или родителя в MVP не поддерживается
- удалять документ может только `owner`
- `editor` может делать все остальные действия внутри документа, включая редактирование контента, title/icon, embeds, collaboration session

## Модель настроек доступа

Для каждого документа должны храниться три независимые политики:

- кто может просматривать документ
- кто может редактировать документ
- кто может комментировать документ

Каждая политика в MVP поддерживает значения:

- `owner_only`
- `space_members`
- `link_holders`

### Значение scope

- `owner_only`:
  действие доступно только владельцу документа
- `space_members`:
  действие доступно всем пользователям, у которых есть доступ к тому же `spaceId`
- `link_holders`:
  действие доступно всем, кто открыл документ по прямой ссылке, включая анонимных пользователей

## Правило вычисления effective role

Роль пользователя вычисляется сервером для каждого документа по следующему правилу:

1. Если пользователь является владельцем документа, роль `owner`.
2. Иначе если пользователь проходит проверку на `edit`, роль `editor`.
3. Иначе если пользователь проходит проверку на `comment`, роль `commentator`.
4. Иначе если пользователь проходит проверку на `view`, роль `guest`.
5. Иначе доступ к содержимому документа запрещен.

Именно effective role должен использоваться во всех API и во frontend.

## Дефолтные значения для новых и существующих документов

Для новых документов по умолчанию:

- `viewAccess = space_members`
- `commentAccess = space_members`
- `editAccess = space_members`

Для уже существующих документов после миграции:

- всем документам также выставляются значения `space_members / space_members / space_members`
- владельцем документа считается пользователь из `createdBy`

Это нужно для того, чтобы не сломать текущий demo-flow и сохранить текущее поведение как базовый сценарий.

## Участники пространства

На первом этапе участником пространства считается пользователь, у которого есть доступ к тому же `spaceId`.

Источник истины по пространствам:

- MWS spaces API для авторизованных пользователей
- кэш доступных `spaceId` для конкретного пользователя на нашей стороне

## Анонимный доступ

### Что поддерживаем

- анонимный пользователь может открыть документ по ссылке, если `view/comment/edit` разрешены для `link_holders`
- UI страницы и редактора визуально не должен дробиться на отдельный "public mode"
- при этом анонимный пользователь получает урезанный набор возможностей относительно полного авторизованного редактора

### Что ограничиваем для анонима

- AI-модули и дополнительные "продвинутые" плагины для анонимного пользователя недоступны
- управление доступом и удаление документа недоступны
- workspace-level функции, завязанные на полноценный аккаунт, не должны считаться обязательными для anonymous flow

### Практическое правило MVP

Анонимный доступ нужен прежде всего для открытия документа по прямой ссылке. Полноценный режим работы со всем workspace для анонима в MVP не является обязательным.

## Комментарии и collaboration

### Комментарии

`commentator` может:

- создавать comment thread по выделению
- писать сообщения в существующие треды
- редактировать свои сообщения
- удалять свои сообщения

`commentator` не может:

- редактировать основной документ
- менять title/icon документа
- менять настройки доступа
- удалять документ

### Collaboration

- пользователи с ролями `owner`, `editor`, `commentator`, `guest`, если им доступен документ, должны видеть presence в документе
- `commentator` должен подключаться к collaboration session, чтобы сразу видеть изменения документа и комментариев
- при этом право на отправку документных изменений определяется не фактом подключения к session, а effective permission на edit

Следовательно, collab/session должна поддерживать read-only и read-write режимы.

## Отображение прав в UI

### Workspace tree

Документы в дереве workspace не должны полностью скрываться, если пользователь не может их открыть на запись.

Нужно показывать:

- обычную иконку документа для `owner`
- иконку документа с карандашом для `editor`
- иконку документа с глазом для `guest` и read-only режима
- иконку документа с замком для недоступного документа

### Locked state

Для недоступного документа в дереве:

- узел показывается в списке
- при наведении должна быть подсказка вида:
  `У вас нет прав для доступа к документу, запросите их у владельца`

### Editor UI

- read-only пользователь должен видеть тот же редактор, а не отдельный экран
- toolbar, slash-menu, AI и mutate-действия должны отключаться на основании capability
- комментарии должны оставаться доступны для `commentator`

## Требования

1. В системе должна появиться page-level модель доступа, привязанная к документу.
2. Для каждого документа должны храниться owner и три политики доступа: `view`, `comment`, `edit`.
3. Роль пользователя должна вычисляться сервером, а не задаваться вручную.
4. Backend должен централизованно проверять доступ к чтению, редактированию, комментированию, удалению и настройке доступа.
5. Frontend должен получать effective role и capabilities вместе с данными страницы.
6. Для `commentator` редактор должен открываться в read-only режиме, но комментарии должны работать.
7. Для `guest` документ должен открываться только на просмотр.
8. Для `editor` должны быть доступны все действия внутри документа, кроме удаления документа и изменения access settings.
9. Для `owner` должны быть доступны все действия, включая настройку прав и удаление документа.
10. Должен поддерживаться анонимный доступ по ссылке для документов со scope `link_holders`.
11. Анонимный пользователь должен получать отдельную visitor identity, пригодную для presence, комментариев и collaboration session.
12. В workspace tree должны отображаться иконки, отражающие effective access пользователя к документу.
13. Недоступные документы должны отображаться как locked item с tooltip.
14. Существующие документы после миграции должны получить дефолтную политику `space_members / space_members / space_members`.
15. Решение должно использовать кэширование пространств и доступных документов, но не делать кэш единственным источником истины.

## Нефункциональные требования

1. Источник истины по правам должен быть в базе данных.
2. Redis-кэш должен использоваться как ускоритель, но не как замена БД.
3. Все mutate-действия должны проверять права на backend, даже если frontend уже скрыл кнопку.
4. Реализация не должна ломать существующий сценарий авторизации через MWS API key.
5. Реализация не должна ломать существующий collaborative flow через Hocuspocus.

## Предлагаемая модель данных

### Prisma

Добавить enum:

- `DocumentAccessScope`
  - `owner_only`
  - `space_members`
  - `link_holders`

Добавить отдельную сущность, например `PageAccessPolicy`, чтобы не перегружать `WikiPage` и держать доступ отдельно от document storage.

Пример полей:

- `pageId`
- `ownerUserId`
- `viewAccess`
- `commentAccess`
- `editAccess`
- `createdAt`
- `updatedAt`

Причины выбрать отдельную таблицу:

- это самостоятельный домен access control
- проще индексировать и расширять далее
- легче делать отдельный service и миграции без смешивания с CRDT/document данными

### Ownership

`ownerUserId` при миграции и при создании новой страницы заполняется из `createdBy`.

## Предлагаемая серверная архитектура

### 1. Новый access service

Добавить модуль, например:

- `backend/src/page-access/`

Сервис должен уметь:

- загрузить policy документа
- определить principal пользователя: owner, authenticated member, anonymous visitor
- проверить membership в пространстве
- вычислить effective role
- вычислить capabilities:
  - `canView`
  - `canEdit`
  - `canComment`
  - `canManageAccess`
  - `canDelete`
  - `canUseAi`
  - `canUseAdvancedPlugins`
- возвращать explainable access result для API и UI

### 2. Единая проверка доступа

Все текущие сервисы должны перестать работать "на доверии" и перед началом mutate/read вызывать access service:

- `PagesService`
- `CommentsService`
- `CollabService`
- `HocuspocusService`
- при необходимости `WorkspaceTreeService`

### 3. Новые backend endpoint'ы

Минимально нужны:

- `GET /api/v1/pages/:pageId/access`
  возвращает effective role, capabilities и policy summary
- `PATCH /api/v1/pages/:pageId/access`
  изменяет policy документа, доступен только owner

Также нужно расширить существующий `GET /api/v1/pages/:pageId`, чтобы он возвращал:

- `access.role`
- `access.capabilities`
- `access.policy`

### 4. Optional auth / anonymous principal

Текущий global auth guard нужно доработать так, чтобы он:

- умел прикреплять авторизованного пользователя, если access token есть
- не падал сразу на ряде public/document routes, где доступ может быть разрешен policy
- умел работать с anonymous visitor identity

Для anonymous visitor в MVP предлагается:

- завести отдельную guest/visitor identity
- хранить ее в cookie или стабильном local storage token
- передавать в API и collab session как отдельного principal

Это нужно, чтобы anonymous пользователь:

- имел устойчивое имя в presence
- мог писать комментарии
- мог участвовать в collab session

## Кэширование

### Цели кэша

- быстро определять, к каким пространствам у пользователя есть доступ
- быстро получать список документов внутри пространства
- минимизировать лишние запросы в MWS и тяжелые выборки

### Предлагаемый подход

База данных остается источником истины для документов и их policy.

Redis используется для двух уровней кэша:

1. Кэш доступных пространств пользователя:

- ключ вида `acl:user:spaces:{userId}`
- хранит список `spaceId`, доступных пользователю
- наполняется после auth/refresh или при первом запросе

2. Кэш документов пространства:

- ключ вида `acl:space:pages:{spaceId}`
- хранит список `pageId` и облегченную access summary по документу
- обновляется при создании документа, архивации, изменении policy

### Правила инвалидации

Нужно сбрасывать кэш:

- при создании новой страницы
- при удалении или архивировании страницы
- при изменении access policy документа
- при смене owner
- при изменении списка доступных пространств пользователя

### Важное правило

Если кэш пустой или устарел, backend обязан уметь восстановить результат из БД и MWS без функциональной деградации.

## Изменения в backend по модулям

### Pages

Нужно:

- при создании страницы создавать и `PageAccessPolicy`
- в `getPage` возвращать access metadata
- в `updatePage` разрешать изменения только `owner/editor`
- в `deletePage` разрешать удаление только `owner`

### Comments

Нужно:

- `listThreads` разрешать всем, у кого есть `canView`
- `createThread/addMessage` разрешать только `canComment`
- `updateMessage/deleteMessage` разрешать только автору сообщения и при наличии `canComment`
- `updateThread` разрешать только при наличии `canComment`

### Collab

Нужно:

- при `openSession` вычислять режим подключения:
  - `read-write` для `owner/editor`
  - `read-only` для `commentator/guest`
- прокидывать capabilities в collab token/context

### Hocuspocus

Нужно:

- на `onAuthenticate` проверять не только pageId из токена, но и collab mode
- на `onChange` игнорировать или запрещать document updates от read-only session
- presence оставлять доступным и для read-only пользователей

### WorkspaceTree

Нужно:

- добавлять в каждый wiki page node access summary:
  - `role`
  - `canView`
  - `canEdit`
  - `isLocked`
- использовать это на фронте для иконок и tooltip

## Изменения во frontend

### API слой

В `frontend/src/shared/api/wikilive.ts` нужно:

- расширить тип `WikiPage`
- добавить типы:
  - `DocumentRole`
  - `DocumentCapabilities`
  - `DocumentAccessPolicy`
- добавить методы:
  - `getPageAccess`
  - `updatePageAccess`

### Auth / bootstrap

Нужно поддержать 2 сценария:

1. Авторизованный пользователь открывает workspace как сейчас.
2. Анонимный пользователь открывает документ по ссылке без логина.

Для этого `AuthGate` больше не должен безусловно блокировать страницу логином, если маршрут ведет на документ, доступный анониму.

### Page editor

Нужно:

- передавать в controller и editor capabilities документа
- переводить Tiptap в `editable = false`, если `canEdit = false`
- отключать mutate-действия:
  - title/icon edit
  - slash-menu insert actions
  - image insert
  - table insert/update actions
  - AI-инструменты для anonymous

### Comments panel

Нужно:

- показывать форму отправки только при `canComment = true`
- скрывать недоступные mutate-действия
- оставлять чтение комментариев при `canView = true`

### Workspace

Нужно:

- показывать иконку по effective role
- показывать locked tooltip
- не давать открыть недоступный документ на редактирование

## План реализации

### Этап 1. База данных и access domain

1. Добавить `DocumentAccessScope` в Prisma.
2. Добавить таблицу `PageAccessPolicy`.
3. Сделать миграцию для существующих страниц:
   - `ownerUserId = wiki_nodes.created_by`
   - `viewAccess = space_members`
   - `commentAccess = space_members`
   - `editAccess = space_members`
4. При создании страницы автоматически создавать default policy.

### Этап 2. PageAccessService

1. Создать `PageAccessService`.
2. Реализовать вычисление effective role и capabilities.
3. Реализовать проверку membership в пространстве.
4. Реализовать Redis-кэш:
   - user -> space ids
   - space -> page ids + access summary
5. Добавить инвалидацию кэша на create/update/delete/access policy change.

### Этап 3. Backend enforcement

1. Встроить access checks в `PagesService`.
2. Встроить access checks в `CommentsService`.
3. Встроить access checks в `CollabService`.
4. Встроить access mode в `HocuspocusService`.
5. Обновить workspace tree, чтобы он возвращал access summary по документам.

### Этап 4. Public/anonymous flow

1. Добавить anonymous visitor identity.
2. Ослабить auth bootstrap для public page routes.
3. Дать возможность открыть документ по ссылке без логина.
4. Ограничить AI/plugins для anonymous capability set.

### Этап 5. Frontend integration

1. Расширить API типы и запросы.
2. Передавать access metadata в page editor.
3. Включить read-only режим Tiptap для `commentator/guest`.
4. Отключить mutate UI, если capability отсутствует.
5. Показать иконки ролей и locked state в workspace tree.
6. Добавить UI настройки доступа документа для owner.

### Этап 6. Настройки доступа документа

В header/page settings добавить owner-only панель, где можно менять:

- кто может просматривать документ
- кто может комментировать документ
- кто может редактировать документ

UI должен:

- показывать текущие значения policy
- объяснять итоговый эффект
- сохранять изменения через `PATCH /pages/:pageId/access`

### Этап 7. Тесты и приемка

1. Unit tests для `PageAccessService`.
2. Integration tests для page/comment/collab access checks.
3. Проверка migration сценария для старых документов.
4. Проверка anonymous read/comment/edit flow для `link_holders`.
5. Проверка read-only collab session.
6. Проверка workspace tree icon mapping.

## Критерии приемки

1. У каждого документа есть owner и policy для `view/comment/edit`.
2. Для документа вычисляется effective role: `owner/editor/commentator/guest`.
3. `owner` может менять доступ и удалять документ.
4. `editor` может делать все внутри документа, кроме удаления документа и изменения access settings.
5. `commentator` может только комментировать и управлять своими комментариями.
6. `guest` может только просматривать документ.
7. Backend не позволяет выполнять mutate-операции при недостаточных правах, даже если фронт ошибся.
8. Анонимный пользователь может открыть документ по ссылке, если policy это разрешает.
9. Анонимный пользователь не получает AI и advanced plugin capabilities.
10. Для `commentator` и `guest` документ открывается в read-only редакторе, без отдельного alternate UI.
11. `commentator` участвует в collaboration session и видит актуальное состояние документа.
12. Read-only участники не могут отправлять document updates в CRDT persistence.
13. В дереве workspace документы отображаются с иконкой по effective role.
14. Недоступные документы отображаются с замком и tooltip.
15. Существующие документы после миграции продолжают работать в режиме `space_members / space_members / space_members`.
16. Реализация покрыта тестами для ключевых сценариев доступа.

## Что сознательно не делаем в этом тикете

- персональные шаринги конкретным пользователям
- наследование прав от папки или родительского узла
- сложную административную модель space admin override
- отдельный публичный workspace mode для анонимного пользователя
- rotation/revocation специальных share-link tokens

## Риски
